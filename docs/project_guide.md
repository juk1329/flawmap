# flawmap 프로젝트 안내서

저장소를 받은 팀원이 이 문서 하나로 환경을 갖추고, 데이터를 받고, 처리와 서비스를 돌리고, 지금까지 알게 된 것을 이어서 개선할 수 있도록 정리했습니다. 2026-11-16 기준입니다.

**데이터는 git에 없습니다.** 애플 도면은 재배포가 금지돼 있고, 공개 데이터셋은 크기가 크고 각자의 라이선스가 있기 때문입니다. 무엇을 왜 받았고 어디에 쓰는지, 어떻게 다시 받는지는 3절에 모두 적었습니다. 팀 서버의 저장소 폴더 `data/`에는 이미 받아 둔 것이 있습니다.

## 목차

1. 프로젝트 한눈에 보기
2. 빠르게 시작하기
3. 데이터 목록
4. 데모용 공개 영상 고르기 (uCO3D)
5. 시스템 구조
6. 실험 결과와 알게 된 점
7. 촬영 안내 (팀용)
8. 조사 결과 요약
9. 한계, 할 일, 팀에게 필요한 것
10. 운영 규칙과 주의

## 1. 프로젝트 한눈에 보기

### 1.1 무엇을 만드나

물건 둘레를 찍은 영상을 올리면, 물건의 3D 모델에 촬영을 맞춰 하자(찍힘, 까짐, 유리 깨짐, 흠집)를 찾고 웹에서 빨갛게 표시합니다. 하자를 누르면 그 하자가 보이는 원본 장면과 영상 시각이 나오고, 찍히지 않은 곳은 빗금으로 표시합니다.

- **지원하는 물건:** 지금은 휴대폰입니다.
  - iPhone 11·12는 애플 도면 치수로 만든 모델을 씁니다.
  - 그 밖의 휴대폰은 촬영본에서 잰 판 모양 모델을 씁니다(실험 단계).
- **서비스 형태:** 검수를 요청한 사람이 촬영본을 올리면 서버가 차례로 처리합니다. 요청자는 결과를 확인한 뒤 링크로 공유하거나 공개 목록에 올리고, 결과를 받은 사람은 읽기 전용으로 봅니다.
- **쓰는 곳 (생각하는 것):** 중고 거래, 대여와 반납, 수리 접수, 보험과 보증, 매입과 검수처럼 물건의 상태를 남기고 나눠야 하는 곳입니다.

### 1.2 배경

- 이 과제는 이전 주제 ISCO(컨베이어 3D 검사 설정 최적화)에서 이어졌습니다. 중간 점검에서 "학부 예산과 규모로는 너무 첨단의 영역"이라는 피드백을 받아 2026-11-04에 주제를 바꿨습니다.
- 같은 기술(사진 → 3D, 원본 모델과 비교, 하자 표시)을 중고 기기 상태 확인에 쓰기로 했습니다. 2026-11-15에 이 저장소(패키지 `flawmap`)를 새로 열었습니다.
- 처음에는 중고 거래 판매자용 서비스로 설계했습니다. 11-16에 일반 검수 플랫폼으로 넓혔습니다.

## 2. 빠르게 시작하기

### 2.1 환경

| 항목 | 내용 |
|---|---|
| 확인한 장비 | Ubuntu 24.04, NVIDIA RTX 3080 Ti (12 GB), CPU 24코어, RAM 61 GB |
| 파이썬 | conda `env_isaaclab` (Python 3.11.15) |
| 주요 패키지 | torch 2.7.0+cu128, numpy 1.26.0(고정), open3d 0.20.0 (CUDA), warp-lang 1.13.0 (GPU 레이캐스팅), OpenCV 4.11 headless, trimesh 4.5.1, manifold3d, pycolmap 4.2.1 (CPU), fastapi 0.115.7, uvicorn 0.29.0, python-multipart, imageio-ffmpeg (HEVC 디코딩), scikit-image 0.26.0, plyfile 1.1.3, remotezip 0.12.6, gdown 6.4.2 |
| 그 밖 | Docker `colmap/colmap:latest`, nvcc 12.9, Node 18. 시스템 ffmpeg은 없음(imageio-ffmpeg의 바이너리를 씀) |

ROS 2가 설치된 셸은 Python 3.10용 `PYTHONPATH`를 내보내므로 먼저 비웁니다.

```bash
source ~/anaconda3/etc/profile.d/conda.sh
conda activate env_isaaclab
export PYTHONPATH=
```

### 2.2 설치

```bash
bash scripts/install_extra_deps.sh --dry-run   # 기존 패키지가 바뀌지 않는지 먼저 확인
bash scripts/install_extra_deps.sh             # scikit-image, plyfile, gdown, remotezip
pip install -e . --no-deps --no-build-isolation   # flawmap 명령
pytest                                          # 단위 시험 52개, 약 1분
```

`--quality max`(6.13절)의 기기 마스크에는 SAM 2가 필요합니다. 메타 공식 저장소의 고정 커밋을 CUDA 확장 없이 넣고, 공개 체크포인트(184 MB, 로그인 없음)를 받습니다. PyPI의 `sam2` 패키지는 메타가 아닌 개인 포크에서 올린 것이라 쓰지 않습니다. 팀 서버에는 11-17에 넣었습니다(새로 들어간 것은 `SAM-2 1.0`, `iopath 0.1.10`뿐).

```bash
SAM2=git+https://github.com/facebookresearch/sam2.git@2b90b9f5ceec907a1c18123530e92e794ad901a4
SAM2_BUILD_CUDA=0 pip install --dry-run --no-build-isolation -c scripts/constraints-isaacsim.txt "$SAM2"
SAM2_BUILD_CUDA=0 pip install --no-build-isolation -c scripts/constraints-isaacsim.txt "$SAM2"
mkdir -p data/models && curl -L -o data/models/sam2.1_hiera_small.pt \
  https://dl.fbaipublicfiles.com/segment_anything_2/092824/sam2.1_hiera_small.pt
```

- `scripts/constraints-isaacsim.txt`는 numpy 1.26.0, psutil 5.9.8, torch 2.7.0+cu128을 고정합니다. 새 패키지는 반드시 `pip install --dry-run -c scripts/constraints-isaacsim.txt`로 기존 패키지가 바뀌지 않는지 먼저 봅니다.
- 실제로 `openxlab` 클라이언트는 requests, urllib3, setuptools 등을 내리려 해서 설치하지 않았습니다.

### 2.3 데모에 필요한 데이터만 받기

팀 서버에서는 이미 `data/`에 다 있으니 건너뜁니다. 다른 컴퓨터에서는:

```bash
bash scripts/fetch_demo_data.sh            # uCO3D 메타데이터 + 데모 영상 5개, 가상 촬영본, 업로드용 zip, three.js
bash scripts/fetch_demo_data.sh --no-full  # 166장짜리 두 면 가상 촬영본은 빼고 (렌더 시간 절약)
```

- uCO3D 메타데이터는 4.9 GB를 받아 13 GB로 풉니다. 이 과정에서 잠시 약 25 GB가 필요합니다.
- 서버에서 그대로 복사해도 됩니다. 예: `rsync -av <서버>:<저장소>/data/synthetic data/`

### 2.4 서비스 띄우기

```bash
bash scripts/serve_detached.sh --port 8000      # 로그아웃해도 계속 돎. 끄기: bash scripts/serve_detached.sh stop
# 또는 앞에서: flawmap serve --port 8000
```

- 기본 주소는 127.0.0.1입니다. 내 PC에서 보려면 `ssh -L 8000:localhost:8000 <서버>` 뒤 브라우저에서 `http://localhost:8000`을 엽니다.
- 같은 네트워크의 다른 기기에서 열려면 `--host 0.0.0.0`을 줍니다.
- 이 서버의 8787 포트는 다른 프로젝트가 쓰므로 피합니다.

| 주소 | 화면 |
|---|---|
| `/` | 첫 화면 |
| `/new` | 검수 요청: 촬영본(zip) 올리기, 또는 공개 영상·가상 촬영본으로 시작 |
| `/s/<요청자 토큰>` | 요청자 화면: 대기 순서와 진행률, 결과, 더 찍을 곳, 공유 설정, 다시 찍어 올리기, 지우기 |
| `/s/<요청자 토큰>/view` | 요청자가 보는 3D 결과 |
| `/r/<공유 토큰>` | 링크를 받은 사람이 보는 읽기 전용 결과 |
| `/gallery` | 공개 목록에 올린 결과 |
| `/ops` | 운영자 화면(서버에서만): 대기열, 처리 시간, 실패, 남은 디스크 |
| `/?run=<이름>` | 개발용: `runs/<이름>/bundle`을 바로 봄 |

### 2.5 발표용 데모 순서 (제안)

1. `/`에서 서비스 소개를 보여 줍니다.
2. `/new` → "공개 영상으로 해 보기"에서 `2712-37354-8763`(청록 테두리 휴대폰, 액정 금)으로 시작합니다. 대기열과 단계별 진행률이 보이고, 약 2.5분 걸립니다.
3. 결과에서 3D 보기와 하자 핀, 근거 장면, "영상에서 보기", 실제 영상 360 보기를 보여 줍니다.
4. "링크로 공유"를 켜고 공유 주소를 다른 창에서 엽니다. 읽기 전용 결과와 검수 기록(번호, 시각, 영상 SHA-256)이 보입니다.
5. 대조군 `9557-8788-41196`(하자 설명이 없는 흰 아이폰)을 함께 보여 주고 한계를 밝힙니다.
6. 가상 촬영본(정답이 있음)으로 보드 경로와 보드 없는 경로의 정확도를 보여 줍니다.
7. 인터넷이 없거나 문제가 생기면 녹화해 둔 백업 영상으로 진행합니다. 녹화는 아직 만들지 않았습니다.

### 2.6 명령 요약

```bash
flawmap board --device iphone-12                                   # A3 촬영 보드 PDF (runs/board/)
flawmap check <Stray 폴더> --device iphone-12 --face-up back        # 첫 촬영 점검: 디코딩, 보드, 모델 맞춤, 겹쳐 그린 그림
flawmap run --device iphone-12 --pass back=<폴더> [--pass screen=<폴더>] --out runs/<이름>
flawmap run --device auto ...                                      # 기종 모름: 크기로 추정, 맞는 도면이 없으면 판 모양 모델
flawmap run ... --poses boardless                                  # 보드가 찍혀 있어도 보드 없이 (비교용)
flawmap run ... --quality max                                      # SAM 2 기기 마스크, COLMAP 자세 보정, 선명한 장면 우선 (6.13절, 느림)
flawmap run ... --board configs/board_a2.yaml                      # 태블릿용 A2 매트
flawmap batch data/captures [--force]                              # 촬영 규격 v2 폴더 일괄 처리 (6.12절, 7.0절)
flawmap board --board configs/board_a2.yaml --size 281.6 215.5 14  # 도면 없는 기기: 길이·폭·모서리 반경으로 안내선
flawmap uco3d <시퀀스> --face-up screen --out runs/uco3d_<시퀀스>    # 공개 uCO3D 영상, 도면 없이
flawmap serve --port 8000                                          # 서비스와 뷰어
python -m flawmap.synth.render_capture data/synthetic/<이름> [--preset demo|small|small-v1|dents] [--background board|wood|paper|cloth] --seed N
python -m flawmap.synth.evaluate runs/<이름> --pass back=data/synthetic/<촬영본>   # 정답과 비교
python -m flawmap.io.download uco3d|omniobject3d|mobilebrick [--sequences ...]   # 공개 데이터

```

### 3.3 uCO3D (공개 휴대폰 영상)

- **무엇:** Meta가 공개한 크라우드 360° 물체 영상 데이터입니다. 사람들이 보통 휴대폰으로 평범한 바닥 위 물건을 돌며 찍었습니다. 보드도 LiDAR도 없어서, 우리가 받은 것 가운데 **가장 일반적인 촬영**입니다.
- **출처:** Hugging Face `facebook/uco3d`(승인 필요 없음). 묶음 목록은 GitHub `facebookresearch/uco3d`의 `dataset_download/category_to_archives.json`에 있습니다. 라이선스는 CC BY 4.0이라 쓸 때 출처를 밝힙니다.
- **받은 방법:** 공식 도구는 상위 범주(`communication_devices`, 영상만 88 GB) 단위로만 받습니다. 그래서 `flawmap/io/download.py`가 `remotezip`으로 HTTP 범위 요청을 보내 `communication_devices/cellular_telephone/*`만 꺼냅니다. `--sequences`를 주면 그 시퀀스만 꺼냅니다.

```bash
python -m flawmap.io.download uco3d                                   # 휴대폰 범주 전부 (약 47 GB + 메타데이터)
python -m flawmap.io.download uco3d --sequences 2712-37354-8763 ... --kinds rgb_videos mask_videos segmented_point_clouds
```

- **서버에 있는 것:**

| 항목 | 개수·크기 | 쓰는 곳 |
|---|---|---|
| `metadata.sqlite` (`metadata.zip` 4.93 GB를 풂) | 13 GB. 표 `sequence_annots`(캡션, 품질), `frame_annots`(프레임별 카메라) | 카메라 읽기(`flawmap/io/uco3d.py`), 캡션 검색 |
| `set_lists/` | 9.6 GB | 쓰지 않음 |
| `rgb_video.mp4` | 1,324개, 37.6 GB | 처리 입력 |
| `mask_video.mkv` | 1,324개, 1.0 GB | 판 맞춤 고르기(마스크 IoU) |
| `segmented_point_cloud.ply` | 1,270개 | 판 모델 첫 위치 |
| `gaussian_splats/` | 1,285개, 7.6 GB | 아직 안 씀 (3DGS 표시 확장 후보) |
| 깊이 | 받지 않음 | 측정값이 아닌 추정값(DepthAnythingV2) |

나머지 시퀀스는 데이터셋 자체에 점군·3DGS가 없습니다.

- **카메라 형식 (`flawmap/io/uco3d.py`):**
  - VGGSfM 결과이고 PyTorch3D 규약입니다. `X_cam = X_world @ R + T`(행벡터), 카메라 축은 +x 왼쪽, +y 위입니다.
  - 내부 파라미터는 `ndc_isotropic`입니다. 픽셀 초점거리는 `f × min(W, H)/2`이고, 주점은 `(W/2 − p_x·s, H/2 − p_y·s)`입니다.
  - 값은 float32 blob이고, `_image_size`는 (H, W)입니다.
  - 왜곡 계수 12개 중 첫 값(k1)만 0이 아니어서 그것으로 프레임을 펴고 핀홀로 씁니다.
  - 주석 프레임은 200장이고 타임스탬프로 영상 프레임을 고릅니다(`round(t × fps)`).
  - **변환 확인:** 분할 점군을 투영하면 마스크 안에 드는 비율이 95.3%(59015-27660-21826), 94.2%(29996-10171-143), 99.1%(3-18937-18174)였습니다.
  - 크기 단위는 SfM 임의 단위라 실제 mm를 모릅니다. 처리할 때 기기 폭을 71.5 mm로 가정합니다.
- **알게 된 것:**
  - 메타데이터가 있는 휴대폰은 1,270개입니다. 짧은 변이 1080 px 이상인 것이 521개, 720 px 이상이 820개이고, 재구성 품질(`_reconstruction_quality_viewpoint`) 중앙값은 1.2입니다.
  - 캡션(자동 생성)에 "iPhone"이 56개 있습니다. 기종은 6, XR, XS, 7 Plus뿐이고 **11·12는 없습니다.**
  - 캡션에 "crack"이 209개 있고, 그중 아이폰이 4개입니다(59015-27660-21826, 29996-10171-143, 65499-34714-54089, 39629-51326-6619). "scratch" 11개, "broken" 4개입니다.
  - 캡션은 대체로 맞지만 하나하나 확인해야 합니다. 예를 들어 63888-22001-16558은 "cracked screen"인데 뒷면이 위로 찍혀 있습니다.

## 5. 시스템 구조

### 5.1 핵심 아이디어: 원본 모델을 좌표계로 쓴다

휴대폰의 유리·금속은 사진만으로 형상을 복원하기 어렵습니다. ISCO에서 흰 물총은 표면 점이 0개였고, 덮은 표면은 4–64%였습니다. 그래서 형상은 원본 모델에서 가져오고, 촬영본은 외관을 읽는 데 씁니다. 프레임마다 카메라 위치를 원본 모델 좌표(mm)로 맞추면 모든 픽셀이 모델 표면의 한 점이 됩니다. 이 대응 하나로 다음이 풀립니다.

- 여러 프레임의 색을 표면에 모아, 시점마다 움직이는 반사와 표면에 고정된 하자를 구별합니다.
- 크기를 mm로 재고 부위 이름을 붙입니다.
- 하자가 잘 보이는 근거 프레임을 계산으로 고릅니다.
- 안 찍힌 곳을 보여 줍니다(일부러 하자 쪽을 안 찍는 경우를 막음).
- 앞면 위·뒷면 위 촬영을 한 좌표계로 합칩니다.

**판형 기기 펼침 좌표:** 액정·후면은 평면 (u, v) mm이고, 프레임은 둘레 s × 높이 z의 띠입니다. 이 좌표가 그대로 텍스처 좌표이자 검출 좌표입니다.
- s = 0이 위 가운데이고, 화면에서 볼 때 시계 방향으로 증가합니다.
- 대칭 위치는 좌우 P − s, 상하 P/2 − s, 180° 회전 s + P/2입니다.

### 5.2 처리 단계 (`flawmap/pipeline.py`)

```
촬영본(면별) ─ prepare_*_pass ─→ 키프레임, 카메라, 원본 모델 정합, 윤곽 표본
                                   │
                          process ─┴→ 표면 색 모으기 → 커버리지 → 하자 검출 → 근거 프레임 → 뷰어 묶음
```

| 단계 | 하는 일 | 코드 |
|---|---|---|
| 읽기 | Stray Scanner 폴더(`rgb.mp4` HEVC, `odometry.csv` 프레임별 위치·fx fy cx cy, 깊이, 신뢰도, 왜곡 표) | `flawmap/io/stray.py` |
| 키프레임 | 시간 창마다 가장 선명한 프레임(라플라시안 분산). 날아간 밝은 픽셀만 노출 실패로 봄 | `flawmap/frames/select.py` |
| 카메라 위치 | 보드 / 보드 없이 / SfM (5.3절) | `flawmap/poses/` |
| 원본 모델 정합 | 실루엣 점을 투영해 전체 해상도 경계에 맞춤 (6자유도, Huber) | `flawmap/anchor/register.py` |
| 표면 색 모으기 | 차트 텍셀(액정·후면 0.1 mm, 프레임 0.05 mm)을 프레임마다 투영하고 깊이 시험을 거쳐 색을 가져옴. GPU 레이캐스팅(Warp) | `flawmap/surface/` |
| 커버리지 | cos > 0.5로 2장 이상에서 본 면적의 비율. 모든 차트를 면적으로 가중 | `flawmap/surface/maps.py` |
| 하자 검출 | 5.5절 | `flawmap/detect/` |
| 근거 프레임 | 점수 = 보이는 비율 × 입사각 × 대비 × 선명도. 1위 다음에 시선이 25° 이상 다른 2장. 빨간 윤곽 확대본(512 px)과 전체(1280 px), EXIF 없음 | `flawmap/evidence/select.py` |
| 뷰어 묶음 | glTF, 4096×2048 텍스처 아틀라스, 하자 덧칠, `defects.json`, 근거 그림, 실제 영상 360용 키프레임, 브라우저용 H.264 영상 | `flawmap/export/bundle.py` |

- 진행률은 (단계, 촬영) 순서의 일정표로 알립니다.
- `run.json`에는 단계별 시간, 다시 찍기 안내(`advice`), 처리 방식(`processing`: 위치 방식, 앵커, 버전, 입력 해시)이 남습니다.
- 처리할 수 없는 촬영은 이유 코드와 다시 찍는 법이 붙은 오류로 멈춥니다(`flawmap/errors.py`): `NO_POSE`, `DEVICE_NOT_FOUND`, `VIDEO_SHORT` 등.

### 5.3 카메라 위치를 잡는 세 가지

| 방식 | 언제 | 방법 | 정확도 (가상) |
|---|---|---|---|
| **보드** (`board`) | 보드가 키프레임 10장 이상에서 보일 때 (`--poses auto` 기본) | ArUco 마커 모서리로 PnP를 먼저 풀고, 체스판 모서리를 투영해 `cornerSubPix`로 다듬어 다시 맞춤. 보드가 안 보이는 프레임은 보드에 맞춘 ARKit 위치 | 0.0022° / 0.089 mm |
| **보드 없이** (`boardless`) | 보드가 없을 때 | 6.7절. ARKit 위치(mm)의 흐름을 기기 외곽으로 바로잡음 | 나무 0.21 px, 종이 0.11 px (모델 재투영 중앙값) |
| **SfM** (`sfm`) | 공개 영상(uCO3D) | 데이터셋의 VGGSfM 카메라를 그대로 쓰고 크기는 가정 | 정답 없음 |

**보드 (`configs/board_a3.yaml`, `flawmap board`):**
- A3 가로에 ChArUco 16 × 11칸, 칸 25 mm, 마커 18 mm, `DICT_5X5_250`.
- 가운데 6 × 9칸(150 × 225 mm)은 무광 회색(RGB 150)이고, 기종 외곽선, "TOP 위" 화살표, 기종 이름을 인쇄합니다.
- 아래 여백에 100 mm 막대가 있습니다. 회색에 닿는 모서리를 빼고 150개 중 80개 모서리를 씁니다.
- 좌표는 원점이 회색 중심, +Y가 화살표, +Z가 종이 위입니다.
- 흑백 무늬가 기기 테두리 바로 뒤에 있으면 외곽 찾기를 방해하고 유리에 비쳐 금처럼 보입니다. 그래서 가운데를 회색으로 덮었습니다.

### 5.4 원본 모델의 세 가지

| 앵커 | 언제 | 방법 |
|---|---|---|
| `cad` | 기종을 앎 (`--device iphone-12`) | 도면 치수 YAML로 만든 모델 (`flawmap/anchor/parametric.py`) |
| `cad-estimated` | 기종 모름 (`--device auto`, 서비스의 "모름") | 범용 판으로 위치를 잡고 크기를 잰 뒤, 길이·폭이 1 mm 안인 도면 모델로 다시 처리 |
| `template` | 맞는 도면이 없거나 공개 영상 | 촬영본에서 잰 둥근 판 (길이, 폭, 두께, 모서리 반경) (`flawmap/anchor/template.py`) |

**도면 기반 모델:**
- 평면 외곽: 모서리 점을 양 끝 접선을 고정한 3차 스플라인으로 잇습니다.
- 몸체: 옆면 단면을 PCHIP로 촘촘히 해 고리를 쌓습니다.
- 앞·뒤 면, 카메라 단차, 렌즈, 버튼은 따로 닫힌 조각으로 만듭니다(레이캐스팅은 첫 충돌만 보므로 합집합을 하지 않음).
- 면마다 부위(screen, back, frame, camera, lens, button)와 펼침 좌표를 붙입니다.
- 버튼·유심·아래 포트 ±3 mm는 프레임 검출 제외 구역입니다.
- 놓인 자세(`rest_pose`)는 무게중심의 투영이 지지 다각형 안에 드는 면에 눕힙니다. 화면이 위면 카메라 단차 때문에 0.75°(12) / 0.72°(11) 기웁니다.

### 5.5 하자 검출 (`flawmap/detect/`)

| 하자 | 방법 | 판정 |
|---|---|---|
| 프레임 까짐 | 프레임 띠에서 같은 높이 줄의 12 mm 이동 중앙값과의 Lab 차이를 줄의 MAD로 나눔. 버튼·유심·포트 ±3 mm는 끔 | z > 8, ΔE > 6 |
| 프레임 찍힘 (윤곽) | 실루엣 점별 부호 있는 잔차(mm)를 둘레 s로 0.5 mm씩 묶어 25 백분위, 3칸 중앙값. 20 mm 이동 중앙값을 빼서 도면과 실물의 완만한 차이를 지움 | z > 6, 0.15 mm 이상, 폭 1 mm 이상. 같은 자리 색 까짐과 합쳐 "프레임 찍힘". 위치만 보고 깊이는 보고하지 않음 |
| 유리 깨짐·흠집 | 국소 배경을 빼고 Sato ridge 필터(0.1–0.2 mm 폭). 중앙값 지도는 깨짐, 80 백분위 지도는 흠집 후보 | 지속성(주변보다 ΔE > 3인 시점 비율) ≥ 0.6이고 길이 3 mm 이상이면 깨짐 |
| 판 모델 전용 | 좌우 대칭인 검출 빼기, 표시부 가장자리 선 빼기, 프레임 보고 안 함 | 6.8절 |

같은 종류가 1.5 mm 안에 있으면 하나로 합칩니다. 기능 하자(배터리, 화면 표시, 터치, 침수)는 범위 밖입니다.

### 5.7 검수 서비스 (`flawmap/service/`, `flawmap/server/app.py`, `web/service/`)

1. 요청자가 `/new`에서 물건 종류(휴대폰만 지원), 기종(기본 "모름"), 물건 이름, 요청자(선택), 면별 zip을 올립니다. 서버의 공개 영상·가상 촬영본으로 시작할 수도 있습니다.
2. **받기 검사(몇 초):** zip 안전성(절대 경로·`..`·심볼릭 링크·4 GB·2만 개 초과 거부), Stray 파일 구성, 프레임 16장 이상, 기기 둘레를 돈 비율(ARKit 궤적, 30° 구간 12개 중), 남은 디스크 ≥ 80 GB를 봅니다. 실패하면 그 자리에서 이유와 다시 찍는 법을 보여 줍니다.
3. 대기열에 넣습니다. 처리기 하나가 하나씩, 별도 프로세스(`python -m flawmap.service.job`)를 메모리 감시와 함께 돌립니다. 서버가 다시 켜지면 죽은 일을 한 번 다시 넣습니다.
4. 요청자 화면이 2초마다 대기 순서, 단계, 남은 시간(지난 처리 시간의 중앙값)을 보여 줍니다.
5. 끝나면 결과, 더 찍을 곳, 공유 설정을 보여 줍니다. 공유는 "링크로 공유"(`published`)와 "공개 목록에도 올리기"(`listed`, 링크 공유가 켜져 있어야 함)의 두 단계입니다.
6. 다시 찍어 올리면 새 검수 번호가 생기고, 끝나면 이전 검수가 "새 검수로 대체됨"이 되며 공유 설정이 넘어갑니다.

**저장과 보안:**
- 저장은 `data/service/`에 합니다(`flawmap.db` SQLite WAL, `inspections/<번호>/upload`, `run`, `job.log`).
- 토큰은 요청자용과 공유용을 따로 둡니다(`secrets.token_urlsafe(16)`). 결과 파일은 토큰이 맞을 때만 내보내고, 경로가 결과 폴더 밖으로 나가면 404입니다.
- 결과에는 검수 번호, 처리 시각, 영상 SHA-256 앞 12자리, 처리 방식, 프로그램 버전이 붙습니다. 요청자도 결과를 고칠 수 없습니다.

**보장하지 못하는 것 (발표에서 밝힘):**
- 찍은 물건이 실제 그 물건인지. 향후 방법은 앱 안에서만 촬영, 화면에 일회용 코드, IMEI 대조입니다.
- 기능 하자.
- 로그인 없는 토큰 주소라 주소가 새면 누구나 봅니다(데모 수준).

## 6. 실험 결과와 알게 된 점

모든 수치는 가상 촬영본 또는 공개 데이터에서 나왔습니다. 실제 팀 촬영본으로는 아직 확인하지 않았습니다.

### 6.1 도면 기반 모델

| 항목 | iPhone 12 | iPhone 11 |
|---|---|---|
| 몸체 (폭 × 길이 × 두께) | 71.52 × 146.71 × 7.39 (도면과 같음) | 75.72 × 150.91 × 8.31 (단면 합. 표기 8.32) |
| 면 수 / 둘레 | 113,682 / 416.66 mm | 160,428 / 432.26 mm |
| 화면 위 기울기 | 0.748° | 0.724° |

고친 것:
- 처음에는 볼록 껍질에서 가장 아래를 향한 면에 눕혀, 화면이 위일 때 렌즈 위에 서 있는 자세가 나왔습니다. 무게중심 조건을 넣어 고쳤습니다.
- 자세 탐색이 46 s 걸려서, 아래를 향하는 순서로 보다가 첫 유효 면에서 멈추게 해 0.1–1.3 s가 됐습니다.
- 점이 5개뿐인 아이폰 11 모서리 스플라인이 변 밖으로 9 µm 넘쳐서 잘랐습니다.

### 6.2 보드로 카메라 위치

- **이상적인 경우:** 높이각 70/45/25/20°에서 재투영 0.07–0.77 px, 회전 < 0.022°, 위치 0.06–0.20 mm였습니다. 가림·흔들림·초점은 넣지 않았습니다.
- **ChArUco 보간 실패:** 낮은 20° 바퀴에서 마커는 44–53개 찾았는데 ChArUco 모서리가 0개였습니다. 마커 모서리로 PnP를 먼저 풀고 체스판 모서리를 투영해 다듬는 방식으로 바꿨습니다.

| | 보드로 위치를 얻은 프레임 | 회전 오차 중앙값/최대 | 위치 오차 중앙값/최대 |
|---|---|---|---|
| ChArUco 보간 | 23/32 | 0.019° / 0.039° | 0.092 / 0.229 mm |
| 마커 + 체스판 다듬기 | **32/32** | **0.0022° / 0.0088°** | **0.089 / 0.119 mm** |

### 6.3 원본 모델 정합

- 처음에는 IoU로 맞추려 했습니다. 하지만 IoU는 정답 근처에서 평평하고, CPU 레이캐스팅으로는 촬영당 몇 시간이 걸립니다. 그래서 외곽 기반 정합으로 정했습니다.
- 첫 판의 3D 점은 실루엣보다 최대 2 px 안쪽의 표면점이라 치우쳤습니다. 각 윤곽 점에서 법선을 따라 맞음→빗나감 경계를 GPU 광선 7번 이분법으로 찾아 고쳤습니다.

| | 회전 | 위치 | 잔차 중앙값 |
|---|---|---|---|
| 첫 판 | 0.069° | 0.185 mm | 0.79 px |
| 이분법 | **0.035°** | **0.113 mm** | **0.245 px (0.044 mm)** |

### 6.4 두 면 가상 데모 (`runs/synth_demo`)

- 뒷면 위·화면 위 각 166장에 하자 7개와 형상 찍힘 1개를 넣었습니다. 처리는 311–320 s(면당 약 110 s, 검출·묶음 약 95 s)였습니다.
- 정합 잔차는 0.229 / 0.240 px이고, 커버리지는 100%였습니다.
- 하자 7개를 모두 맞는 자리에서 찾았습니다. 찍힘은 s 160.25(정답 160)에서 0.40 mm로 잡혔습니다.
- **흠집이 깨짐으로 분류됩니다.** 가상 음영에서 흠집이 대부분 시점(84%)에 보이기 때문입니다. 렌더러의 흠집을 각도 의존으로 고쳤지만 실제 흠집으로 확인해야 합니다.
- `defects.json`이 6.8 MB였던 것을 윤곽 단순화(1.5 px)로 1.37 MB로 줄였습니다.

### 6.5 윤곽으로 찍힘 찾기 (다섯 번 고쳐서 됨)

1. 찍힘이 띠 높이 방향으로도 3 mm만 눌려, 위에서 본 윤곽(가장 바깥)이 바뀌지 않았습니다. 낙하 찍힘처럼 띠 전체 높이를 누르게 했습니다(`radius_v`).
2. 정합의 점만 쓰니 윤곽 표본이 3,327개뿐이었습니다. 면당 최대 100장의 윤곽 점을 모두 쓰는 단계(`edge_residuals`)를 넣었습니다.
3. 정합 마지막 탐색 폭 ±3 px로는 0.8 mm 찍힘(300 mm에서 약 4 px)이 창 밖이었습니다. ±8 px로 넓혔습니다.
4. 외곽 꼭짓점(직선 구간 최대 4 mm 간격)에 맞춰 s를 정해 표본이 뭉쳤습니다. 0.1 mm 간격으로 다시 뽑아 KD 트리로 찾았습니다. 834칸 중 826칸이 찼습니다.
5. 찍힘 없는 촬영본에서 거짓 찍힘 4개(약 0.3 mm)가 나왔습니다. 둥근 가장자리의 반사선처럼 1.5 px 떨어진 두 경계 때문이었습니다. 칸 통계를 25 백분위로, 3칸 중앙값을 더했습니다.

| 촬영본 | 표본 | 퍼짐 | 찾은 찍힘 |
|---|---|---|---|
| 찍힘 2개 (0.8, 0.4 mm) | 19,903 | 0.016 mm | s 159.75 (0.46 mm), s 299.75 (0.23 mm) |
| 찍힘 없음 | 9,291 | 0.022 mm | 없음 |

깊이는 실제보다 작게 나옵니다(0.8 → 0.46 mm). 그래서 위치만 보고 깊이는 보고하지 않습니다.

### 6.6 커버리지 오류 (11-16 고침)

한 면만 찍었는데 97%로 나왔습니다. 원인은 둘이었습니다.
- 찍지 않은 면의 차트가 계산에서 빠졌습니다.
- 프레임 텍셀(0.05 mm)이 면 텍셀(0.1 mm)보다 4배 무겁게 들어갔습니다.

모든 차트를 넣고 면적으로 가중하니 한 면 55.8%, 두 면 100%가 됐습니다.

### 6.7 보드 없는 촬영 (`flawmap/poses/boardless.py`)

**방법:**
1. ARKit 세계(중력이 y축)를 z가 위인 좌표로 돌리고 mm로 씁니다.
2. 키프레임 광축이 가장 가깝게 모이는 점을 기기 중심으로 봅니다. 바닥 높이는 **앞 30% 프레임의** LiDAR 깊이에서 높이의 최빈값입니다(뒤 프레임은 이미 흘러 있음).
3. **방향 찾기:** 원본 모델의 위·아래 윤곽 고리를 투영합니다. 보이는 옆면이면 아래 고리, 아니면 위 고리를 씁니다. 수평 회전 6° × 위치 4 mm 격자에서 방향 비교를 더한 경계 거리로 점수를 내고, 1.5° × 1 mm로 다듬습니다. 카메라가 겨눈 점 근처를 약하게 선호합니다.
4. **180° 쌍둥이:** 외곽이 같으므로, 뒷면이 위일 때 모델의 렌즈 자리가 어두운 쪽을 고릅니다(맞는 쪽 56, 반대쪽 −0.5). 어느 후보도 렌즈가 어둡지 않으면(대비 < 15) "기기를 찾지 못함"으로 멈춥니다.
5. **함께 맞추기:** 기기는 바닥에 놓인 채(방향과 위치만), ARKit 흐름은 시간의 매끄러운 함수(6자유도 매듭, 사이는 선형)로 모든 키프레임의 외곽에 맞춥니다. 시간 창을 앞 40% → 70% → 전체로 늘리며 앞에서 찾은 흐름을 이어받습니다.

### 6.8 판 모양 모델 (도면 없음)

**크기 맞추기 (`fit_dimensions`):**
- 외곽 정합의 6자유도에 너비·길이·두께의 로그 배율 3개를 더해 풉니다. 매 회 새 크기로 모델을 다시 만들고, 마지막에 모서리 반경(6/8/10/12 mm)을 잔차로 고릅니다.
- 보드 촬영본(카메라 정확)에서 크기를 5–8% 틀리게 시작했습니다. 결과는 146.78 × 71.71 × 7.21 mm(정답 146.71 × 71.52 × 7.39)이고, 오차는 0.07 / 0.19 / 0.18 mm였습니다.
- **기종 추정 (`--device auto`):** 보드 없는 나무 바닥에서 146.29 × 71.11 × 7.84를 재서 iPhone 12(0.42 mm 안)로 맞혔습니다. 결과는 기종을 알려 준 처리와 같았습니다(221 s).
- **한계:** iPhone 12와 12 Pro는 몸체 크기가 같아 크기만으로 못 가릅니다.

**공개 영상(uCO3D)에서 알게 된 것과 규칙:**
1. **구조물이 하자로 잡힘:** 처음 결과에서 점수가 높은 것은 수화부 구멍, 홈 버튼 고리, 흰 테두리와 검은 표시부의 경계였습니다. 이들은 좌우 대칭이고 하자는 거의 그렇지 않습니다. 그래서 장치 세로 중심선에 대해 뒤집었을 때 다른 검출(자기 포함, 1.5 mm 팽창)에 30% 넘게 겹치면 뺍니다(`drop_mirror_symmetric`).
2. **첫 위치:** 분할 점군의 주축이 휴대폰을 가로질러 40 × 71 mm 판이 맞춰진 경우가 있었습니다. 면 평면을 강건하게 맞추고 최소 외접 사각형으로 잡는 방법(`plate_box`)을 더했습니다. 그러나 다른 영상에서는 이 방법이 더 나빴고, 외곽 잔차(0.398 vs 0.404 px)로는 둘을 가르지 못했습니다. 그래서 두 시작점으로 모두 맞추고 **데이터셋 마스크와 실루엣의 IoU**가 높은 쪽을 고릅니다.
3. **판 모양이 아님:** 맞춘 길이/폭이 1.4–2.6 밖이면 멈춥니다.
4. **프레임:** 위에서 내려다본 영상에서 프레임 띠는 스치듯 보이고, 모르는 기종의 버튼·포트는 가리지 못합니다. 그래서 휴대폰마다 6–52개의 거짓 까짐이 나왔습니다. 판 모델에서는 프레임 검출을 보고하지 않습니다.
5. **표시부 가장자리:** 한쪽만 잡히면 대칭 시험을 빠져나갑니다. 길이 12 mm 이상, 폭 2 mm 이하, 축과 6° 안, 바깥 테두리에서 10 mm 안인 선은 뺍니다(`drop_border_lines`).

### 6.11 Stray 카메라 축 규칙 (11-17 고침)

- 첫 실제 촬영본(아이폰으로 찍은 아이패드 두 면)에서 확인했습니다. Stray Scanner의 `odometry.csv` 자세는 **이미 OpenCV 카메라 축**(x 오른쪽, y 아래, z 앞)입니다.
- 그런데 `flawmap/io/stray.py`는 여기에 ARKit 축을 바꾸는 `diag(1, -1, -1)`을 한 번 더 곱하고 있었습니다. 가상 촬영본은 같은 뒤집기를 거꾸로 적용해 썼기 때문에 시험에서는 드러나지 않았습니다.
- 증거: 장면마다 LiDAR로 바닥 평면을 맞춰 바닥 법선을 비교했습니다. 뒤집기를 빼면 법선이 1.3° 안에서 일치하고 ARKit 위쪽(+y)을 향합니다. 뒤집기를 넣으면 25–27° 흩어집니다.
- 고친 것: `ARKIT_TO_CV_CAM`(읽기)과 `CV_TO_ARKIT_CAM`(가상 촬영본 쓰기)을 둘 다 단위 행렬로 바꿨습니다. 실제 녹화 발췌(`tests/data/stray_floor/`, 자세와 깊이 8장)로 `tests/unit/test_stray_convention.py`가 이 규칙을 고정합니다.
- **고치기 전에 만든 가상 촬영본(`data/synthetic/`)과 그 zip은 새 규칙과 맞지 않습니다.** 다른 컴퓨터에서는 해당 폴더를 지우고 `scripts/fetch_demo_data.sh`로 다시 만듭니다(`gt.json`이 있으면 건너뛰기 때문입니다).
- 팀 서버에서는 11-17에 6개 촬영본의 `odometry.csv` 회전만 새 규칙으로 바꾸고(`R @ diag(1, -1, -1)`), `scripts/make_sample_zips.sh`로 업로드 zip을 다시 만들었습니다. 영상·깊이·정답은 그대로입니다. 같은 설정으로 다시 렌더한 것과 비교하면 회전 차이 0.000002°, 위치 차이 0입니다. 바꾸기 전 파일은 `data/synthetic_before_axis_fix/`에 있습니다.
- 바꾸기 전에 처리한 결과(`runs/synth_*` 등)는 그대로 맞습니다. 그때는 읽기와 쓰기가 같은 뒤집기를 써서 서로 맞았기 때문입니다.
- 실제 녹화 두 개(아이패드, 각 40장)로 다시 확인했습니다. 새 규칙에서는 장면별 바닥 법선이 평균 방향에서 중앙값 1.4°·0.4°만 벗어나고 위(+y)를 향합니다. 예전 규칙에서는 중앙값 20°·7°로 흩어지고 아래를 향합니다.

### 6.12 일괄 처리 `flawmap batch` (11-17)

촬영 규격 v2(7.0절)로 찍은 기기 폴더를 사람의 판단 없이 처리합니다. 무엇을 넣고, 어떻게 처리하고, 결과를 언제 받아들일지는 기기 폴더의 `manifest.yaml`과 `configs/batch.yaml`(품질 기준)이 정합니다. 기준 파일의 해시가 요약에 남아서, 같은 입력과 기준이면 같은 판정이 나옵니다.

```bash
flawmap batch data/captures                 # manifest.yaml이 있는 기기 폴더 전부
flawmap batch data/captures/<기기> --force  # 하나만, 이미 있는 결과도 다시
```

| 단계 | 하는 일 | 미달이면 |
|---|---|---|
| 받기 검사 | 녹화마다 길이(궤도 45초 이상), 기기 둘레를 돈 비율(75% 이상), LiDAR 깊이 | `recapture`: 처리하지 않고 이유를 남김 |
| 처리 | 궤도 녹화를 `pipeline.run`에 넣음. 매트가 A3/A2면 보드로, `none`이면 보드 없이 위치를 잡음. 기종 `auto`면 바닥 모자이크로 판 크기를 재고(`anchor/floor_outline.py`) 도면과 대조. 매트가 보이는 녹화는 바닥 측정을 건너뛰고 보드 경로가 크기를 잼 | 촬영 문제(`FlawmapError`)는 `recapture`, 그 밖의 오류는 `failed` |
| 결과 검사 | 면마다 외곽 잔차 1 px 이하, 커버리지(두 면 90%, 한 면 50%), 매트를 썼으면 보드로 위치를 잡았는지 | `warn`: 결과는 남기고 이유를 적음 |

결과는 `runs/batch/<이름>/`(평소 결과 폴더, 뷰어 묶음 포함)에, 요약은 `runs/batch/summary.json`과 `summary.md`(기기마다 한 줄: 상태, 기종, 크기, 하자 수, 커버리지, 외곽 잔차, 위치 방식, 이유)에 남습니다. 문제가 있는 기기(`recapture`, `failed`)가 하나라도 있으면 종료 코드가 1입니다. 시험: `tests/unit/test_batch.py`.

**도면 없는 기기(태블릿)를 위해 함께 고친 것** (실제 아이패드 촬영본에서 발견):
- `anchor/floor_outline.py`(새 파일): LiDAR 바닥 + 바닥 투영 모자이크로 크기·모서리·위치·방향을 잼. 바닥에서 다른 녹화가 깨끗하게 잰 모양을 고정해 그림자 번짐을 막고, 윗면 높이(두께)는 무늬 있는 면에서 재서 나눠 씀.
- `poses/boardless.py`: 바닥 높이를 광축이 모이는 점이 아닌 카메라 아래에서 찾음(광축이 덜 모이면 그 점이 바닥보다 80–270 mm 아래로 감). 측정한 판의 자세를 후보로 먼저 시도.
- `surface/maps.py`: 큰 면은 텍셀을 키움(면당 300만 개 이하; 13인치 태블릿 0.15 mm).
- `anchor/template.py`: 모서리 반경 후보를 크기에 맞춤.

**매트 위 촬영과 기종 `auto` (11-17 고침):**
- 바닥 모자이크는 매트가 있으면 기기 대신 종이를 잽니다. 가상 A3 촬영본(`iphone12_dent_small`)에서 417.4 × 290.9 mm(종이는 420 × 297)를 쟀습니다. 그 결과 `--device auto`가 iPhone 12 대신 종이 크기의 판 모델로 끝났습니다(하자 18개, 커버리지 48.9%).
- 그래서 `--poses auto`에서는 키프레임 8장 중 3장 이상에 보드 마커가 보이면 그 녹화의 바닥 측정을 건너뜁니다. 크기는 예전처럼 보드 경로가 휴대폰 판에서 시작해 잽니다. 같은 촬영본에서 146.61 × 71.54 mm → iPhone 12, 하자 2/2, 오탐 0으로 바닥 측정이 생기기 전 코드와 같습니다.
- 시험: `tests/unit/test_floor_plate_board.py`.
- 남은 한계: 매트 위의 태블릿은 기종 `auto`로 아직 재지 못합니다. 휴대폰 판에서 시작하기 때문입니다(9.1절).

### 6.13 텍스처 선명도와 `--quality max` (11-17)

첫 실제 촬영본(아이패드 뒷면)의 텍스처가 흐렸습니다. 원인을 재기 위해, 로고 부근 75 × 80 mm를 장면마다 0.1 mm로 펴서 비교했습니다. 선명도는 경사 에너지입니다.

| 합치는 방식 | 지금 자세(ARKit + 외곽선) | COLMAP 자세 |
|---|---|---|
| 모든 장면의 중앙값 (원래 방식) | 17 | 21 |
| 선명한 장면 20%만 | 122 | 173 |
| 선명한 장면만 + 장면끼리 2D 정렬 | 193 | 210 |
| 가장 선명한 한 장 | 509 | 510 |

- **주원인은 흔들린 장면입니다.** 17–21초에 한 바퀴를 돌아서 장면들의 선명도 중간값이 가장 선명한 장면의 1/5이었고, 중앙값으로 합치면 디테일이 사라졌습니다. COLMAP으로 정렬해도 모든 장면을 섞으면 흐립니다(17 → 21).
- **두 번째 원인은 면 안쪽의 장면 간 어긋남입니다.** 외곽선은 0.2 mm로 맞는데도 장면끼리 중간값 2.1 mm, 상위 10% 7 mm가 어긋났습니다. ARKit 흐름을 시간에 대해 부드러운 곡선으로 보정하기 때문입니다. COLMAP(바닥 무늬로 번들 조정)은 101장을 모두 정렬했고(0.76 px), 장면 간 어긋남을 상위 10% 기준 2.6 mm로 줄였습니다.

`--quality max`(일괄 처리 기본값, `configs/batch.yaml`의 `process.refine`, `process.sharp_views`, `process.segment`)는 다음 세 가지를 켭니다.
1. **COLMAP 자세 보정**(`poses/colmap.py`, 보드 없는 경로에만):
   - 키프레임으로 SIFT, 순차 매칭, 번들 조정을 합니다. 순차 매칭은 이웃 12장과 2, 4, 8…장 떨어진 장면을 짝지어 한 바퀴를 닫습니다. 전수 매칭은 101장에 5,050쌍이라 너무 느렸습니다.
   - 내부 파라미터는 Stray 값으로 고정합니다.
   - 카메라 중심 기준 닮음 변환으로 같은 좌표계에 옮기고, 넓은 탐색 창(24 → 2.5 px)으로 기기를 다시 정합합니다.
   - 등록률 80% 미만, 재투영 1.5 px 초과, 카메라 중심 차 30 mm 초과면 쓰지 않습니다. 다시 정합한 결과도 마스크 IoU가 보드 없는 자세보다 0.003 넘게 낮거나 외곽 잔차가 1.5배를 넘으면 쓰지 않습니다. 마스크가 없으면 외곽 잔차가 1.1배 안일 때만 씁니다.
   - 실패해도 처리는 계속됩니다.
2. **선명한 장면 우선**(`surface/maps.py`의 `prefer_sharp_views`): 면마다 장면별 선명도를 그 장면이 본 텍셀에서 잽니다(같은 영역 평균 이미지 대비 비율). 상위 30%만 남기고, 선명한 장면이 3개 미만인 텍셀은 모든 장면을 씁니다. 텍스처, 검출, 커버리지가 모두 이 선택을 따릅니다.
3. **SAM 2 기기 마스크**(`segment/device_masks.py`, 설치는 2.2절):
   - 첫 정합으로 키프레임 6장에 기기 상자를 주면, SAM 2(hiera-small)가 모든 키프레임에서 기기를 따라갑니다. 마스크는 프레임의 1/4 크기입니다.
   - 쓰는 곳은 셋입니다: 투영한 모델과의 IoU로 정합을 따로 검사하고(일괄 처리 기준 0.95), COLMAP 자세를 쓸지 정하고, 마스크 밖 표본을 텍스처에서 뺍니다.
   - 외곽 잔차만으로는 바닥 판자 이음새에 붙은 1 cm 어긋남을 못 가렸습니다(아이패드 화면, IoU 0.880 대 0.979).

이 데이터의 한계: 가장 선명한 한 장과는 아직 2.5배 차이가 납니다. 선명한 장면이 적고 근접 녹화가 없기 때문입니다. 촬영 규격 v2(면마다 60–90초를 천천히, 15–20 cm 근접 녹화)가 그 차이를 줄이는 쪽입니다.

**팀 서버에서 다시 확인 (11-17):** SAM 2와 체크포인트를 넣은 뒤, 같은 아이패드 녹화를 `--device auto --poses boardless`로 처리했습니다.

## 7. 촬영 안내 (팀용)

### 7.0 촬영 규격 v2 — 일괄 처리용 (11-17)

`flawmap batch`가 사람의 판단 없이 처리할 수 있도록 촬영 조건을 고정합니다. 실제 촬영본(아이패드)에서 생긴 문제는 대부분 조건이 매번 달라서였습니다. 찍는 사람의 그림자, ARKit 흐름 최대 30 mm, 위에서만 내려다본 촬영, 17–21초짜리 짧은 녹화가 그 예입니다.

| 항목 | 규격 |
|---|---|
| 매트 | 휴대폰은 A3 보드(`configs/board_a3.yaml`), 태블릿은 **A2 매트**(`configs/board_a2.yaml`, 회색 영역 275 × 300 mm). 무광 용지에 실제 크기(100%)로 인쇄하고, 칸 크기(25 mm)를 자로 재서 `manifest.yaml`의 `square_mm`에 적습니다. 도면이 없는 태블릿을 `device: auto`로 처리하려면 지금은 매트 없이(`board: none`) 찍습니다(6.12절) |
| 매트 만들기 | 도면이 있는 기종은 `flawmap board --device iphone-12`, 도면이 없으면 `flawmap board --board configs/board_a2.yaml --size 281.6 215.5 14`(길이, 폭, 모서리 반경 mm)로 놓을 자리를 인쇄합니다 |
| 놓기 | 회색 영역의 외곽선에 맞추고, 기기 윗부분(수화부·카메라 쪽)이 화살표를 향하게 둡니다 |
| 조명 | 천장 조명처럼 고른 빛. 찍는 사람의 그림자가 매트에 지지 않게 조명을 등지지 않습니다 |
| 기기 상태 | 케이스·필름을 벗기고, 화면을 끄고, 마른 천으로 닦습니다 |
| 녹화 앱 | Stray Scanner(LiDAR가 있는 iPhone Pro / iPad Pro), 깊이·신뢰도 기록 켜기 |

**면마다 녹화 두 개**(화면 위, 뒷면 위 → 모두 네 개):

| 녹화 | 하는 법 | 쓰는 곳 |
|---|---|---|
| `orbit` | 기기가 화면의 30–60%(휴대폰 25–35 cm, 태블릿 40–60 cm), 낮은(20°)·중간(45°)·높은(70°) 높이로 한 바퀴씩, 마지막에 위에서 한 번. **60–90초** | 카메라 위치, 형상, 커버리지 |
| `close` | **15–20 cm**까지 다가가 면을 지그재그로 천천히 훑고, 테두리를 따라 한 바퀴. 30–60초 | 흠집 해상도(약 0.12 mm/픽셀) |

**폴더와 `manifest.yaml`**: 기기 하나에 폴더 하나입니다. Stray 녹화 폴더를 그 안에 이름을 바꿔 넣습니다.

```
data/captures/<기기 이름>/
  manifest.yaml
  screen_orbit/  screen_close/  back_orbit/  back_close/     (Stray Scanner 폴더 그대로)
  gt.yaml                                                     (선택: 실제 하자 기록, 7.5절)
```

```yaml
name: ipad-pro13-silver        # 결과 폴더 이름
device: auto                   # configs/devices의 기종(slug), 모르면 auto
board: a2                      # a3 | a2 | none (매트 없이 찍었을 때)
square_mm: 25.0                # 인쇄한 매트의 칸을 잰 값
passes:
  - {face: screen, kind: orbit, path: screen_orbit}
  - {face: back,   kind: orbit, path: back_orbit}
  - {face: screen, kind: close, path: screen_close}
  - {face: back,   kind: close, path: back_close}
```

- 처리: `flawmap batch data/captures`(기기 폴더 여럿) 또는 `flawmap batch data/captures/<기기>`. 품질 기준은 `configs/batch.yaml`에 있고, 결과와 요약표는 `runs/batch/`에 남습니다(6.12절).
- `close` 녹화는 지금은 받기 검사만 하고 처리에는 넣지 않습니다. 근접 텍스처 단계가 생기면 씁니다.

### 7.1 준비물

| 준비물 | 설명 |
|---|---|
| 촬영용 휴대폰 | LiDAR가 있는 iPhone Pro(12 Pro 이후)나 iPad Pro에 **Stray Scanner**(무료, App Store, iOS 18.6 이상). LiDAR가 없는 기기에서는 Stray Scanner를 쓸 수 없습니다 |
| 찍을 기기 | 하자 있는 아이폰, 하자 없는 아이폰 (아이패드는 나중) |
| 바닥 | 기기와 색이 다른 면. 검은 기기면 밝은 책상이나 흰 종이, 흰 기기면 어두운 천 |
| 인쇄 보드 (정밀 모드, 선택) | `flawmap board --device <기종>`이 만든 `runs/board/board_a3-v1_<기종>.pdf`를 **A3에 실제 크기(100%)**로 인쇄("용지에 맞춤" 끔), 무광 용지 |
| 자, 캘리퍼 | 보드 칸이 25.0 mm인지, 100 mm 막대가 맞는지. 기기의 길이·폭·두께·카메라 단차 |
| 대역 하자 재료 | 은색 테이프(1–2 mm 조각), 화면 금처럼 보이는 장난 필름 |

### 7.2 기기 상태와 조명

1. 케이스와 보호 필름을 벗깁니다.
2. 화면을 끕니다. 개인 정보가 찍히지 않고 화면 반사가 일정해집니다.
3. 마른 천으로 앞·뒤·테두리를 닦습니다. 지문과 먼지는 하자로 잘못 잡힙니다.
4. 기종 이름을 확인합니다(설정 > 일반 > 정보 > 모델 이름).

조명은 천장 조명이나 흐린 날 창가처럼 고른 빛이 좋습니다. 직사광선, 한 점 조명, 촬영 중 조명 변화, 찍는 사람의 그림자는 피합니다.

### 7.3 찍는 법

1. 기기를 바닥 가운데 놓습니다. 처리 프로그램은 카메라들이 가장 많이 겨눈 점 근처에서 기기를 찾습니다. 보드를 쓰면 회색 영역의 외곽선에 맞추고 윗부분(수화부)이 화살표 쪽을 향하게 합니다.
2. Stray Scanner로 녹화합니다(깊이와 신뢰도 기록 켜기). 기기가 화면의 30–60%를 차지하게(약 25–35 cm) 둡니다.
3. **천천히** 세 바퀴를 돕니다.
   - 낮은 높이(약 20°): 테두리 찍힘에 꼭 필요합니다. 처음 30% 영상으로 기기를 찾으므로 이 바퀴로 시작합니다.
   - 중간(약 45°), 높은 높이(약 70°)
4. 마지막에 위에서 한 번 훑습니다. 면마다 60–90초가 적당합니다.
5. 화면이 위인 촬영과 뒷면이 위인 촬영을 따로 녹화합니다. 뒷면 위에서는 **카메라 렌즈가 보여야** 위아래를 구분합니다.
6. 반짝이는 바닥이나 체크무늬처럼 촘촘한 바닥은 피합니다.

### 7.4 촬영 목록 (약 12개)

| 기기 | 면 | 횟수 |
|---|---|---|
| 하자 있는 아이폰 | 화면 위, 뒷면 위 | 각 3회 (같은 결과가 나오는지 보려고) |
| 하자 있는 아이폰, 보드 위 + 보드 없이 | 뒷면 위 | 각 1회 (두 경로 비교) |
| 하자 없는 아이폰 | 화면 위, 뒷면 위 | 각 1회 |
| 하자 없는 아이폰 + 대역 하자 | 화면 위(균열 필름), 뒷면 위(테두리 은색 테이프) | 각 1회 |

**첫 촬영 1개(하자 있는 아이폰, 뒷면 위)를 가장 먼저** 올려 주세요. `flawmap check`로 실제 휴대폰에서 디코딩·위치 잡기·정합부터 확인합니다.

### 7.5 실제 하자 기록 (`gt.yaml`)

하자마다 적고 근접 사진을 함께 올립니다. 위치는 가장 가까운 모서리에서 테두리를 따라 잰 거리입니다.

```yaml
device: iphone-12
defects:
  - id: 1
    type: dent               # dent(찍힘) | chip(까짐) | scratch(흠집) | crack(깨짐)
    where: right side        # left/right/top/bottom side, 또는 top-left corner 등 (화면을 보고)
    from_corner: top-right
    distance_mm: 32
    length_mm: 2.5
    photo: dent1.jpg
    note: 도장이 벗겨져 은색이 보임
```

대역 하자도 같은 형식으로 붙인 위치를 적습니다.

### 7.6 올리는 곳

- **서비스:** Stray Scanner의 기록 폴더를 파일 앱에서 길게 눌러 "압축"한 zip을 `/new`에 올립니다.
- **서버에서 직접:** `data/captures/<기기>_<면>_<회차>/`(예: `data/captures/iphone-defect_back_1/`, 면은 `screen` 또는 `back`)에 두고 `flawmap check`, `flawmap run`을 돌립니다. `gt.yaml`과 사진은 `data/captures/<기기>_gt/`에 둡니다.

### 8.7 첫 계획에서 바뀐 것 (독립 검토 반영)

| 바뀐 것 | 이유 |
|---|---|
| 찍힘의 주 경로를 외곽 → 외관(색)으로. 외곽은 확인용 | SAM 2 마스크가 256×256이라 1–1.5 mm보다 작은 변화가 묻힘. IoU ≥ 0.97도 평균 0.7 mm 오차를 허용 |
| 정합을 IoU → 외곽 기반으로 | IoU는 정답 근처에서 평평하고 CPU 레이캐스팅으로는 몇 시간 |
| 마스크를 SAM → 정합된 원본 모델 투영으로 | SAM 2는 900프레임이면 약 11 GB GPU |
| 사실적 모델을 3DGS → 실제 키프레임 360 보기로 | 유리·금속 반사에 3DGS가 약함 |
| 보드 가운데를 회색 시트 + 외곽선·화살표로 | 흑백 무늬가 외곽 찾기를 방해하고 유리에 비침. 화살표가 180° 모호성을 없앰 |
| Stray Scanner를 주 입력으로 | 기본 카메라 앱은 렌즈 전환, 손떨림 보정, HDR, 가변 프레임률 |
| 물리 대역 하자 추가 | 정답 위치를 자로 잴 수 있는 실제 영상 |

### 8.8 ISCO에서 배운 것

- COLMAP은 같은 입력에서도 결과가 달랐습니다(표면 64% → 46%).
- 재투영 오차가 좋아도 모델이 틀릴 수 있습니다(0.71 px인데 카메라 415 mm 오차).
- 흰 저무늬 플라스틱은 표면 점이 나오지 않았습니다.
- 카메라 등록은 배경 무늬를 따라갑니다(나무·카펫은 모두 등록, 무늬 없는 책상은 25장 중 10·16장).
- 등록 품질만으로 180° 판 뒤집힘을 가리기 어려웠습니다. 이 문제는 보드 없는 경로에서 렌즈로 풀었습니다.

## 9. 한계, 할 일, 팀에게 필요한 것

### 9.1 알려진 한계

- 실제 팀 촬영본은 아이패드 한 대(두 면, 17·21초, 매트 없음)뿐이고 하자 정답이 없습니다. 하자 수치는 모두 가상 촬영본과 공개 데이터에서 나왔습니다.
- 매트 위의 태블릿은 기종 `auto`로 크기를 재지 못합니다. 매트가 보이면 바닥 측정을 건너뛰고 휴대폰 판에서 시작하기 때문입니다(6.12절).
- 실제 아이패드(표준 처리)에서 하자가 25개 나왔고 23개가 뒷면입니다. 텍스처에 겹쳐 보면 카메라 부위 5개, 로고 가장자리 4개, 외곽선을 따라 11개, 그림자가 진 오른쪽 아래 3개입니다. 판 모델은 카메라와 로고 자리를 모릅니다. 하자 정답이 없어 진짜 하자가 있는지는 모릅니다.
- `--quality max`는 흔들림이 없는 가상 촬영본에서는 장면만 줄입니다(6.13절).
- 가상 흠집이 깨짐으로 분류됩니다. 보드 없는 촬영에서는 흠집 하나를 놓쳤습니다(원인 미확인).
- 보드 없는 경로:
  - 실제 ARKit 흐름의 모양(가상은 시간에 선형), 실제 LiDAR 바닥 잡음, 반짝이는 바닥은 시험하지 않았습니다.
  - 화면이 위일 때 180° 쌍둥이 구분은 외곽 잔차에 맡기는데 시험하지 않았습니다.
  - 촘촘한 무늬 바닥에서는 멈춥니다.
- 판 모양 모델:
  - 깨진/깨끗한 구분이 약합니다.
  - 위아래 방향을 모릅니다.
  - 크기는 가정값입니다(공개 영상).
  - 프레임 하자는 보고하지 않습니다.
  - 카메라 단차·버튼 근처가 덜 정확합니다.
- iPhone 12와 12 Pro는 크기로 못 가립니다.
- Stray Scanner 렌즈 왜곡 표(`distortion/`)는 방향(왜곡/보정)을 실제 촬영으로 확인한 뒤 적용합니다. 지금은 두 방향을 다 시험해 보드 재투영이 10% 넘게 줄어드는 쪽만 쓰고, 아니면 펴지 않습니다.

## 10. 운영 규칙과 주의

### 10.1 환경

- conda `env_isaaclab`만 씁니다. 새 가상환경을 만들지 않습니다.
- 셸마다 `export PYTHONPATH=`를 먼저 합니다(ROS 2의 Python 3.10 경로 때문).
- 새 패키지는 `--dry-run`과 `-c scripts/constraints-isaacsim.txt`로 기존 패키지가 바뀌지 않는지 확인한 뒤 설치합니다.
- 서버의 다른 conda 환경(`feature_splatting`, `gaussian_splatting` 등)은 쓰지 않습니다.

### 10.2 큰 작업과 메모리

- 2026-11-02에 OOM으로 systemd와 tmux가 함께 죽은 적이 있습니다. 렌더나 처리처럼 오래 걸리는 작업은 `bash scripts/with_memory_guard.sh <스크립트 파일>`로 감쌉니다. 남은 메모리가 8 GB 밑이면 프로세스 묶음을 멈춥니다.
- 표준 입력이 닫히므로 heredoc 대신 스크립트 파일을 넘깁니다.
- CPU는 같은 서버의 가상머신이 많이 씁니다(24코어 중 약 20). GPU 경로와 낮은 해상도 계산을 우선합니다.

### 10.3 디스크

- 남은 공간 50 GB가 하한이고 처리용 30 GB를 더 남깁니다. 다른 작업 때문에 남은 공간이 크게 바뀌므로(181 → 877 GB를 오간 적 있음) 받기 전마다 다시 확인합니다.
- 11-16 기준 남은 공간은 약 800 GB이고, `data/`는 약 74 GB입니다(uCO3D 66 GB, MobileBrick 진행 중).

### 10.4 오래 도는 프로세스

- 터미널이나 에이전트 세션의 배경 작업은 세션이 끝나면 함께 꺼집니다. 서버와 내려받기는 세션과 떼어 띄웁니다.
  - `bash scripts/serve_detached.sh --port 8000`
  - `setsid nohup bash scripts/download_datasets.sh mobilebrick > runs/logs/launch_mobilebrick.log 2>&1 < /dev/null &`
- 프로세스를 이름으로 끌 때 `pkill -f "<스크립트 이름>"`은 그 명령을 실행한 셸 자신과도 맞을 수 있습니다. `pkill -f "fetch_dem[o]"`처럼 패턴에 대괄호를 넣습니다.

### 10.6 git

- 원격 저장소는 `https://github.com/juk1329/flawmap`이고 기본 브랜치는 `main`입니다. 받기: `git clone https://github.com/juk1329/flawmap.git`.
- 올릴 때는 저장소에 쓰기 권한이 있는 계정이 필요합니다. HTTPS로 올리면 비밀번호 대신 GitHub 개인 액세스 토큰을 넣습니다. SSH로 올리려면 그 계정에 등록된 SSH 키가 있어야 합니다.
- 커밋 메시지는 영어로 무엇을 왜 바꿨는지 적습니다.
- `docs/`에서는 이 안내서만 git에 올라갑니다. 개인 작업 메모는 `docs/` 안에 두면 올라가지 않습니다.
- 작업할 때마다 이 안내서의 상태 표(1.4절), 데이터 목록(3절), 결과(6절)를 함께 고칩니다.
